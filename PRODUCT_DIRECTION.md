# Направление развития Game Product Analytics

Этот документ фиксирует рабочую концепцию продукта, практики исследования рынка Steam и предлагаемые этапы развития. Это направление для обсуждения и проверки, а не описание уже реализованных функций или утверждённый roadmap.

## 1. Зачем нужен продукт

Помочь небольшой игровой команде понять:

- с какими играми сравнивать свою концепцию;
- какого опыта ожидают игроки выбранной ниши;
- какие механики и решения конкурентов стоит изучить;
- какие технические и дизайнерские ошибки особенно дорого повторить;
- насколько разумны ожидания по цене, спросу и масштабу проекта.

Основной результат — проверяемые продуктовые гипотезы и решения для своей игры. Анализ отзывов через LLM является одним из инструментов этого процесса.

Проект предполагается использовать в двух целях:

1. Исследовать рынок и референсы для собственной игры.
2. Создать портфолио-кейс для позиции Product Manager, показывающий исследование проблемы, приоритизацию, реализацию и проверку результата.

## 2. Основной сценарий

Основная сущность продукта — **исследование**, например: «Проверка концепции тактической игры с управлением отрядом».

Исследование содержит:

- описание своей игры и ограничения команды;
- вопросы и решения, для которых нужны данные;
- набор сравниваемых игр с объяснением их выбора;
- исходные данные и подтверждающие материалы;
- наблюдения, выводы и альтернативные объяснения;
- гипотезы, способы их проверки и журнал принятых решений.

Рабочий процесс:

**Описать концепцию → сформулировать вопросы → выбрать аналоги → сравнить механики и отзывы → проверить доказательства → сформировать гипотезы → проверить их на своей игре.**

## 3. Приоритетные возможности

| Возможность | Практическая польза | Ограничения |
| --- | --- | --- |
| Анализ достоинств и проблем по отзывам | Формирование требований и гипотез | Нужны источники, точные категории и проверка выводов |
| Сравнение тем отзывов нескольких игр | Выявление повторяющихся ожиданий ниши | Выборки и правила разметки должны быть сопоставимыми |
| Поиск по конкретным механикам | Подбор содержательных референсов | Нужен собственный словарь признаков и несколько типов источников |
| Поиск прямых и косвенных конкурентов | Формирование группы для исследования | Кандидатов подтверждает человек; сходство механик не доказывает общую аудиторию |
| Срез тегов и жанров | Поиск и позиционирование | Теги не описывают весь игровой опыт |
| Сравнение рейтингов, цен, отзывов и онлайна | Рыночный контекст | Исторические ряды нужно накапливать или получать у поставщика |
| Профиль ожиданий аудитории | Понимание требований к глубине, удобству и реиграбельности | Авторы отзывов не представляют автоматически всю аудиторию |
| Оценки продаж и объёма ниши | Сценарии бюджета и ограничение ожиданий | Только оценки с диапазонами, источниками и методологией |

Первый продуктовый фокус: **сравнение отзывов группы игр, подробные игровые признаки и выводы для своей концепции**. Рыночные показатели дополняют это ядро.

## 4. Поиск игр по подробным признакам

Жанров недостаточно для точного поиска. Например, управление юнитами через выбор и приказы встречается в разных жанрах и может давать разный игровой опыт.

Признаки стоит разделять по измерениям:

| Измерение | Примеры |
| --- | --- |
| Объект управления | Персонаж, отряд, армия, поселение |
| Способ управления | Прямой контроль, выбор объекта и приказ, назначение задач |
| Выбор объектов | Клик, рамка выделения, группы, вся команда |
| Течение времени | Реальное время, пауза с приказами, пошаговый режим |
| Автономия | Точное выполнение команд, приоритеты, самостоятельные действия |
| Основные решения | Позиционирование, тайминг, состав отряда, экономика, логистика |
| Последствия поражения | Перезапуск, потеря юнитов, потеря прогресса, продолжение с последствиями |
| Визуальные свойства | Перспектива камеры, стиль, читаемость объектов и интерфейса |

Пример запроса:

> Найти игры с управлением небольшим отрядом через выбор и приказы, с тактической паузой, где позиционирование важнее скорости кликов. Изометрия желательна, строительство базы не нужно.

### Источники признаков

- Описание игры: заявленные механики и структура.
- Руководства и обучение: конкретные способы управления.
- Геймплейные видео: поведение систем во времени.
- Скриншоты: перспектива, визуальный стиль, элементы интерфейса.
- Отзывы: восприятие механик и проблемы их использования.
- Ручная проверка: спорные и важные признаки.

Каждый признак должен иметь значение, подтверждающий источник и статус: **подтверждено / предположение / неизвестно**. Отсутствие упоминания механики не означает её отсутствие.

Первая версия поиска может работать на десятках вручную проверенных игр одной области. LLM извлекает признаки из материалов, обязательные условия фильтруют кандидатов, желательные условия помогают ранжировать. Результат объясняет совпадения и различия.

### Типы отношений между играми

- **Прямой конкурент:** похожее обещание игроку, опыт и контекст покупки.
- **Косвенный конкурент:** похожая потребность закрывается другим игровым способом.
- **Механический референс:** полезен для изучения конкретной системы.
- **Визуальный референс:** полезен для камеры, стиля и читаемости.
- **Коммерческий аналог:** сопоставим по цене, масштабу, стадии и модели выпуска.

Одна игра может быть хорошим референсом управления и плохим ориентиром по продажам.

## 5. Практический анализ отзывов

Структура полезного вывода:

**Наблюдение → интерпретация → значение для нашей игры → способ проверки.**

Для каждой темы нужны:

- понятное название и описание;
- количество уникальных отзывов с упоминанием темы и размер выборки;
- контекст: период, язык, наигранное время, версия, если известна;
- последствия, которые описывают игроки;
- подтверждающие цитаты и ссылки на исходные отзывы;
- возможные причины и альтернативные объяснения;
- применимость к своей концепции;
- гипотеза и проверка через прототип, интервью или плейтест.

### Пример структуры вывода

Следующий пример вымышленный и иллюстрирует формат, а не результат исследования.

**Проблема:** потеря контроля над отрядом в узких проходах.

- Наблюдение: в 24 из 240 изученных отзывов упоминаются застревание, игнорирование приказов или непредсказуемое движение.
- Контекст: бои в ограниченном пространстве.
- Последствие: потери воспринимаются как несправедливые.
- Возможные причины: поиск пути, коллизии, недостаточная обратная связь о выполнении приказа.
- Значение для своей игры: при необратимой гибели юнитов предсказуемость управления особенно важна.
- Проверка: сценарий с несколькими юнитами в узком проходе; наблюдать застревания, отмены приказов и понимание игроком происходящего.
- Доказательства: в реальном отчёте здесь должны быть ссылки и фрагменты конкретных отзывов.

Отзывы показывают переживание игрока, но не всегда устанавливают корневую причину. Нужно различать технические неисправности, неудобство управления, непонятные правила, несоответствие ожиданиям и намеренные особенности дизайна.

### Содержание отчёта по группе игр

1. За что игры любят и какую ценность важно сохранить.
2. Что игроки считают базовым требованием.
3. Какие проблемы повторяются в нескольких играх.
4. По каким вопросам аудитория расходится во мнениях.
5. Где есть сигналы неудовлетворённой потребности.
6. Какие выводы применимы к своей игре и с какими ограничениями.
7. Какие эксперименты стоит провести дальше.

Противоречащие свидетельства необходимо сохранять. Желание одних игроков убрать микроменеджмент и любовь других к нему могут указывать на разные сегменты аудитории.

### Правила работы с выборками

- Анализировать положительные и отрицательные отзывы.
- Делать срезы по времени, языку и наигранным часам на момент отзыва.
- Не ограничиваться только самыми полезными отзывами.
- Считать уникальные отзывы с темой, а не повторения слов.
- Показывать долю темы внутри каждой игры и её распространённость между играми.
- Если отрицательные отзывы переотобраны для диагностики, явно обозначать это.
- Не переносить доли из отзывов на всех игроков: 24 из 240 отзывов не означает, что с проблемой столкнулись 10% аудитории.

## 6. Рыночные показатели и их интерпретация

### Размер ниши и продажи

Первый вопрос: какие результаты наблюдаются у сопоставимых игр и какой масштаб вложений разумно рассматривать?

Полезные показатели:

- число сопоставимых релизов за выбранный период;
- медиана и разброс количества отзывов;
- темп появления новых отзывов;
- оценки продаж за одинаковый срок после выпуска;
- концентрация результатов у лидеров;
- цены и история скидок;
- появление новых заметных участников.

Оценки продаж должны показывать источник, метод и диапазон. Сначала разумнее использовать внешние оценки; собственная модель требует данных для проверки.

Нельзя суммировать владельцев нескольких игр и называть результат уникальной аудиторией ниши. Накопленные продажи за много лет также не равны годовому спросу. Владение игрой, её покупка и фактическая игра — разные показатели.

### Ценовые ожидания вместо «платёжеспособности»

Доход и бюджет игрока нельзя надёжно определить по отзывам. Исследовать можно:

- за что игроки оправдывают цену;
- что вызывает ощущение «слишком дорого»;
- ожидание скидок;
- достаточность объёма контента;
- отношение к DLC;
- воспринимаемое соотношение цены и ценности.

Цена на витрине не равна цене покупки. Высокая цена и хорошие отзывы сами по себе не доказывают высокую готовность платить.

### Профиль ожиданий аудитории

Вместо общей характеристики «требовательная аудитория» исследовать конкретные ожидания: глубину решений, разнообразие прохождений, скорость входа, терпимость к повторению, ценность сюжета, отношение к наказанию за ошибки, кооператив, удобство и техническое качество.

Много жалоб на FPS в одной игре может характеризовать её оптимизацию, а не требования всей ниши.

### Онлайн

CCU — число одновременно играющих подключённых к Steam пользователей. Текущий CCU доступен через официальный API, но исторический ряд нужно накапливать или получать у поставщика.

- CCU не равен размеру аудитории.
- Снижение CCU не является прямым измерением retention.
- Низкий онлайн завершённой сюжетной игры не обязательно плохой результат.
- Общий онлайн не гарантирует заполненность конкретного региона или режима мультиплеера.
- Для сравнения нужны одинаковые окна после релиза и учёт обновлений и скидок.

### Теги

Полезно показывать распространённые теги выбранной группы, отличия подгрупп и соответствие тегов своей концепции. Теги являются инструментом поиска и позиционирования, но не полной моделью механик. Популярность тега не доказывает влияние на продажи; редкое сочетание может означать как возможность, так и отсутствие спроса.

## 7. Методика исследования

1. **Начать с решения:** определить, что выбирается — концепция, механика, цена, масштаб или позиционирование.
2. **Задать критерии аналогов:** фиксировать причины включения и исключения игр.
3. **Изучать разные исходы:** лидеров, средние результаты и малозаметные проекты.
4. **Сравнивать сопоставимые стадии:** одинаковые сроки после релиза, отдельно учитывать Early Access.
5. **Разбирать игровой опыт:** использовать матрицу механик, играть или смотреть геймплей.
6. **Размечать отзывы по единой схеме:** определить категории и проверять качество разметки.
7. **Сопоставлять источники:** отзывы, витрину, геймплей, метрики и заявления разработчика.
8. **Проверять выводы на своей игре:** формировать эксперименты и критерии результата.

Совпадение изменения метрик с патчем или скидкой не доказывает причинность. Для каждого объяснения нужно учитывать другие события и альтернативные причины.

## 8. Предлагаемые этапы развития

### Этап 1. Одно исследование для собственной игры

- Описать концепцию и ограничения команды.
- Выбрать три решения, которые исследование должно поддержать.
- Собрать примерно 10–15 игр разных типов.
- Разметить ключевые механики и отзывы по общей схеме.
- Подготовить выводы и проверить хотя бы одну гипотезу.

Часть работы выполняется вручную. Цель — понять, какие операции стоит автоматизировать.

### Этап 2. Сравнение группы игр

Первый цельный сценарий: выбрать игры, получить матрицу ожиданий и проблем, проверить источники и сформировать гипотезы.

Минимальные возможности: сохранённые исследования, набор игр, структурированные темы, переход к источникам, сравнение, ручное исправление выводов, отчёт и журнал решений.

### Этап 3. Поиск по подробным признакам

Добавить разбор описания своей игры, поиск кандидатов, объяснение совпадений и ручное подтверждение набора. Оценивать качество поиска на проверенной разметке.

### Этап 4. Рыночный контекст и мониторинг

Добавить внешние оценки продаж, рыночные срезы, динамику отзывов и онлайна, события, скидки, сценарии бюджета и отслеживание изменений ниши.

### Что отложить

- Универсальную подробную классификацию всего Steam.
- Собственный прогноз продаж без проверочного набора данных.
- Автоматический единый рейтинг перспективности ниши.
- Точные психологические и финансовые портреты покупателей по отзывам.

## 9. Портфолио для Product Manager

Сильный кейс показывает полный цикл:

1. Конкретная проблема и существующие способы её решения.
2. Проверка проблемы у разработчиков или продюсеров.
3. Выбор узкого сценария и аргументация приоритетов.
4. Реализация инструмента.
5. Проверка качества анализа и удобства использования.
6. Решения, которые инструмент помог принять.
7. Ошибки, ограничения и изменения после обратной связи.

Предлагаемые метрики:

- время до первого проверенного полезного вывода;
- доля выводов, подтверждённых указанными источниками;
- частота существенных исправлений человеком;
- релевантность первой десятки результатов поиска;
- пропуски известных релевантных игр в тестовом наборе;
- повторное использование для следующего исследования;
- стоимость и длительность анализа.

Сравнивать результат с ручным исследованием и обычной LLM, получившей те же материалы. Использование для своей игры дополнить несколькими внешними пользователями.

Проект особенно подходит для Game Product, AI Product и аналитических B2B-позиций. Он не заменяет кейс внутренней игровой аналитики с retention, воронками и экономикой; при необходимости его можно дополнить плейтестами и метриками своего прототипа.

## 10. Источники и доступность данных

Первичный ресёрч проведён 6 октября 2026 года. Документация и условия доступа могут меняться. Материалы поставщиков описывают их собственные методы и результаты, а не независимые гарантии точности.

- [Steam: API отзывов IUserReviewsService](https://partner.steamgames.com/doc/webapi/IUserReviewsService). Старый `/appreviews` помечен устаревшим. Новый API документирует фильтры дат, наигранного времени и другие параметры; это нужно учесть при развитии сборщика.
- [Steam: теги](https://partner.steamgames.com/doc/store/tags). Верхние 20 тегов участвуют в видимости и определении сходства; специфичные теги могут быть информативнее общих.
- [Steam: текущий онлайн](https://partner.steamgames.com/doc/webapi/ISteamUserStats#GetNumberOfCurrentPlayers). Источник текущего CCU, не готовой исторической серии.
- [How To Market A Game: исследование аналогов](https://howtomarketagame.com/2021/01/25/how-to-spy-on-your-competition/). Подбор по игровому опыту, визуальному уровню и модели издания. Старые численные эвристики не следует принимать за постоянные правила.
- [How To Market A Game: общий процесс](https://howtomarketagame.com/2021/07/12/how-to-market-your-indie-game-a-10-step-plan/). Исследование жанровых ожиданий, успешных и неудачных проектов, общение с игроками.
- [Gamalytic: методология оценок продаж](https://gamalytic.com/blog/how-to-accurately-estimate-steam-sales). Сопоставление нескольких методов и описание их ограничений. В опубликованном историческом тесте простой множитель отзывов отклонялся более чем на 50% примерно у 30% рассмотренных игр.

## 11. Ближайший шаг

Для выбора пилотного исследования нужно определить:

1. Что игрок делает большую часть времени и ради какого опыта.
2. На какой стадии собственная игра и какие решения вызывают сомнения.
3. Какие 3–5 игр уже считаются близкими и по каким причинам.

После этого подготовить первое исследование и только затем уточнять состав функций и roadmap тулсета.
